## 0. 착수 전에 걸리는 것 — 실측

조사에서 나온 제약이다. 설계보다 이게 먼저다.

| # | 사실 | 영향 |
|---|---|---|
| 1 | **미래 일정이 0개** (마지막 날짜 2026-08-08). `schedule-dates/sync` 가 `while (cursor <= today)` 로 **오늘까지만** 만든다 | 신청을 붙일 대상이 없다. **선행 작업** |
| 2 | 일정 테이블에 `date` 만 있다 (시간·장소·정원 없음) | "몇 시, 어디, 몇 명까지"를 못 적는다 |
| 3 | 출석은 **사후 계산** — 그날 이벤트가 있으면 참여로 인정 (`/attendance`) | 사전 신청은 별개 개념. 기존 출석 로직을 건드리지 않는다 |

| 5 | 계정 **21명 / 정회원 37명 (57%)** | 사용자 결정: 가입 독려 선행 |

## 1. 참여신청 (Phase 1)

### 1-1. 선행 — 미래 일정 생성 ✅ 완료 (2026-08-14)

`schedule-dates/sync` 의 생성 범위를 `start_date ~ 오늘` → `start_date ~ +8주` 로 넓혔다
(`FUTURE_WEEKS = 8`). 미라클모닝농구단에 **예정 일정 8개**(8/15 ~ 10/3)가 생겼다.

구현하며 실제로 걸린 두 가지 — 둘 다 그냥 범위만 넓혔으면 조용히 터졌다:

1. **미실시 자동 판정** — 새로 만든 미래 날짜는 당연히 영상 0·기록 0이다. `d > cutoffYmd`
   가드가 이미 있어 살았지만, 이제 그 줄이 미래 일정을 지키는 역할까지 한다.
   없었다면 만들자마자 8개가 전부 '미실시'로 접혀 신청을 못 받았다. 주석으로 못 박았다.
2. **유튜브 연동** — 대상 선정이 "경기가 없는 날은 영상이 먼저 올라왔을 수 있다"며 `true` 를
   내주고 있었다. 미래 8주치가 전부 대상이 되어 **동기화마다 8번씩 헛검색**(매번 0건)이
   나갈 참이었다. `d <= todayYmd` 로 잘랐다.

`FUTURE_WEEKS = 8` 의 근거: 두 달치면 "다음 달에 나갈 수 있나"까지 답이 나오고,
그 이상은 체육관 대관이 확정되지 않아 나중에 지울 날짜만 는다.

### 1-2. 일정에 붙일 정보 ✅ 완료 (마이그레이션 098)

```sql
ALTER TABLE league_schedule_dates
  ADD COLUMN start_time    time,          -- null = 미정
  ADD COLUMN place         text,
  ADD COLUMN capacity      int,           -- null = 무제한, CHECK (capacity > 0)
  ADD COLUMN rsvp_closes_at timestamptz;  -- null = 마감 없음
```

전부 nullable 이다. **과거 32개 날짜에 소급 입력을 요구하지 않기 위해서**다.

화면(`/schedule`)도 함께 손봤다:

- 미래 날짜에 **「예정」** 배지. 편집 모드에서 시간·장소·정원을 입력한다(`PATCH`)
- 입력된 항목만 그린다 — '미정'을 나열하면 과거 32개가 전부 「미정 · 미정」으로 도배된다
- 예정 일정에는 **박스스코어 버튼을 아예 두지 않는다.** 치르지 않은 경기의 비활성 버튼은
  자리만 차지하고 누를 일이 영영 없다
- 분기 탭: 예정 일정은 경기가 없어 분기 지도에 안 잡힌다 → 없을 때만 분기 기간으로 되짚는다.
  안 하면 분기 탭을 누르는 순간 예정 일정이 통째로 사라진다
- ⚠ 장소 입력칸 때문에 편집기를 **모듈 최상단 컴포넌트**로 뺐다. 렌더 함수 안에 두면
  한글 IME 조합이 글자마다 끊긴다

### 1-3. 신청 테이블

```sql
CREATE TABLE league_rsvp (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  league_id uuid NOT NULL REFERENCES leagues(id) ON DELETE CASCADE,
  schedule_date_id uuid NOT NULL REFERENCES league_schedule_dates(id) ON DELETE CASCADE,
  account_id uuid NOT NULL REFERENCES league_user_accounts(id) ON DELETE CASCADE,
  status text NOT NULL CHECK (status IN ('going','not_going','maybe')),
  assigned_team_id uuid REFERENCES league_teams(id),  -- 1-3b 참조. null = 기본 배정 따름
  assigned_by uuid,                                   -- 수동 배정한 운영진
  note text,
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE (schedule_date_id, account_id)
);
```

**`account_id` 로 잡는 이유** — `league_player_id` 로 잡으면 계정 없는 사람 몫을 아무나 넣을 수 있다.
UNIQUE 로 한 사람 한 응답을 못 박는다(중복 신청은 데이터가 아니라 버그다).

**상태를 3종으로 두는 이유** — `going/not_going` 만 두면 "아직 안 정함"과 "불참"이 구분되지 않아,
총무가 **누구를 더 찔러야 하는지** 알 수 없다. 미응답(행 없음)과 `maybe` 도 다른 상태다.

### 1-3b. 팀 배정 — 정규회원은 자동, 비정규회원은 대기

사용자 결정(2026-08-14): *"팀소속이 정해진 정규회원은 바로 해당 팀으로 배정되며, 비정규회원은
대기 상태, 각 팀장 및 운영진의 회의하여 각 팀에 배치됩니다."*

**정규/비정규를 가르는 새 플래그를 만들지 않는다.** 이미 데이터에 있다 —
`league_player_quarters.team_id` 가 그 분기의 소속이다. 실측(2026-08-14, 3분기):

| 구분 | 인원 | 판정 |
|---|---|---|
| 정규회원 | 19명 | 현재 분기 `team_id` 있음 → 신청 즉시 그 팀 |
| 비정규회원 | 18명 | `team_id` 없음 → **대기** |

계정 22개는 **전부** `league_player_id` 로 선수와 연결돼 있다(22/22). 계정만 있고 선수가 없는
행이 없으므로 소속 조회가 항상 성립한다.

#### `assigned_team_id` 는 "기본값과 다를 때만" 채운다

⚠ 신청할 때 정규회원의 소속팀을 **복사해 저장하면 안 된다.** 그 뒤 운영진이 그 사람의 분기
소속을 바꾸면, 아직 치르지도 않은 경기의 배정이 옛 팀에 굳어버린다.

| `assigned_team_id` | 뜻 | 화면 |
|---|---|---|
| `null` + 분기 소속 있음 | 자동 배정 | 그 분기 소속팀 |
| `null` + 분기 소속 없음 | **대기** | 「배정 대기」 |
| 값 있음 | 운영진이 직접 배치 | 그 팀 (자동 판정을 덮는다) |

즉 **저장은 예외에만** 한다. 이 리그가 `league_team_quarter_overrides` 에서 이미 쓰는 방식과
같은 꼴이다 — 기본값은 계산하고, 어긋나는 것만 행으로 남긴다.

이 규칙은 정규회원을 하루만 다른 팀에 넣는 경우(인원 안 맞을 때)도 그대로 처리한다.

#### 운영진 화면

- 「배정 대기」 목록 — `going` 인데 배정이 안 잡힌 사람
- 팀별 현 인원과 **함께** 본다. 대기자만 따로 보면 어느 팀이 비었는지 모른 채 배치하게 된다
- 배정은 되돌릴 수 있어야 한다(회의 중에 바뀐다) → `assigned_team_id` 를 null 로 되돌리는 버튼

⚠ **배정과 실제 출전은 다른 데이터다.** 경기 후 실제 뛴 팀은 지금도 `league_game_players` 가
기록한다. 신청 배정을 그 기록에 자동 반영하지 않는다 — 당일에 바뀌는 일이 흔하고,
어긋나면 스탯이 틀린다.

### 1-3c. 대관 없는 주 — 신청을 받지 않는다 ✅ 완료

사용자 결정(2026-08-14): *"대관이 없는 일정을 어드민이 지정하면 해당 주간은 신청이 없는 방향"*.

**새 컬럼을 만들지 않고 `is_skipped` 를 그대로 쓴다.** 담는 사실이 같기 때문이다 —
**이 날은 경기가 없다.** 기존 자동 판정(영상 0 + 기록 0 + 7일 경과)은 지난 주를 사후에 접고,
이건 앞으로의 주를 미리 접을 뿐이라 **시제만 다르다.**

플래그를 둘로 나눴다면 "둘 다 true 면?" 같은 답 없는 조합이 생기고, 신청 차단 조건도
두 곳을 봐야 한다. 화면 라벨만 시제로 가른다:

| 시제 | 배지 |
|---|---|
| 미래 + `is_skipped` | 「대관 없음」 |
| 과거 + `is_skipped` | 「미실시」 |

- 어드민 토글은 **되돌릴 수 있다** — 대관이 뒤늦게 잡히는 일이 흔하다
- 차단은 **서버에서** 한다(`loadDate` 가 `is_skipped` 를 거른다). 날짜를 직접 지정해도 막힌다

### 1-4. 화면 ✅ 완료

| 위치 | 내용 |
|---|---|
| **홈 최상단** | 다음 경기 · 날짜/시간/장소 · `참석 / 미정 / 불참` · 참석 N명 · 내 배정 팀 |
| **경기 > 일정** | 시간·장소·정원 입력, 대관 없음 토글 |

⚠ **홈 최상단에 둔다.** 이 카드는 '보는 것'이 아니라 '하는 것'이다. 매주 전원이 한 번씩
눌러야 값이 생기는데 탭 안이나 스크롤 아래에 두면 아무도 안 누른다.

구현에서 걸린 것:

- 홈은 `unstable_cache` 로 통째로 캐시된다. **내 응답은 사람마다 다르므로 그 캐시에 섞이면
  남의 응답이 보인다.** → 카드 안에서 따로 받아온다. 대신 로딩 중에도 높이를 유지해
  아래 내용이 밀리지 않게 했다
- 로그인은 라우트가 아니라 **모달**이다(`mm-open-login` 이벤트). `/login` 으로 보내면 404
- 비로그인에게도 경기 정보는 보여준다 — 가입해야 신청할 수 있다는 걸 아는 것이
  가입 독려의 실질이다. 빈자리로 두면 이런 게 있는 줄도 모른다

### 1-4b. 고정 대관 ✅ 완료 (마이그레이션 100)

사용자 요구(2026-08-14): *"매주 대관 및 시간은 동일하나 가끔 일정이 없거나 대관장소 및 시간이
변경되는 건이 있습니다. 설정에서 고정 대관 및 시간은 정해두고 디폴트로 설정되게 한 후,
예외만 수동으로 변경"*.

`leagues.default_start_time / default_place / default_capacity` 를 두고,
`league_schedule_dates` 의 같은 필드는 **다를 때만** 채운다.

⚠ **일정 행에 기본값을 복사해 넣지 않는다.** 복사하면 "체육관이 바뀌었다"고 설정을 고쳐도
이미 만들어진 예정 일정 8개가 옛 장소에 굳는다. 읽을 때 합친다(`applyVenueDefaults`).
`assigned_team_id`·`league_team_quarter_overrides` 와 같은 원칙이다.

- 편집기는 기본값을 **미리 채워 넣지 않고 placeholder 로만** 보여준다("기본 상암 체육관").
  채워 넣으면 저장하는 순간 그 날의 예외로 굳는다
- 고정 대관을 그대로 따르는 날에는 **「고정 대관」** 이라고 밝힌다. 안 밝히면 그 날만
  따로 넣어 둔 값인 줄 알고, 설정을 바꿨을 때 왜 여기까지 바뀌는지 모른다
- **과거 날짜에는 씌우지 않는다** — 오늘 정한 장소를 지난 32경기에 소급하면 없던 사실이 생긴다

곁다리로 `PATCH /api/leagues/[leagueId]` 의 **대량 할당**을 막았다. 받은 객체를 그대로
`update()` 에 넘기고 있어서 요청 하나로 `edit_pin`·`slug`·`team_id` 까지 바꿀 수 있었다.
화면이 그런 요청을 안 보낼 뿐 막혀 있진 않았다 → 허용 컬럼 목록으로 통과시킨다.

### 1-4c. 팀별 참가현황 — 명단을 깔고 표시만 바꾼다 ✅ 완료

사용자 결정(2026-08-14): *"정규 회원 명단은 일단 각 팀별로 리스트를 다 보여준 뒤,
참석 여부를 클릭하면 표시처리를 바꾸는 방식"*.

**응답한 사람만 보여주면 아직 안 누른 사람이 화면에서 사라진다.** 그게 총무가 가장 알고 싶은
정보다("누구를 찔러야 하나"). 그래서 정규회원 전원을 팀별로 깔고, 응답은 **표시로만** 바꾼다.

| 상태 | 표시 |
|---|---|
| 참석 | 초록 체크 (`--mm-positive`) |
| 미정 | 물음표 (`--mm-yellow-strong`) |
| 불참 | 붉은 X (`--mm-negative`) · 이름 흐리게 |
| 미응답 | 빈 동그라미 |

- **색만으로 뜻을 전하지 않는다** — 모양이 넷 다 다르고 `aria-label` 도 붙는다
- **비정규는 응답한 사람만** 올린다. 18명 전원을 깔면 카드가 명단이 아니라 전화번호부가 된다
- **미가입자를 구분 표기**한다. 계정이 없으면 영영 응답할 수 없는데 회색으로만 두면
  "왜 응답을 안 하지"로 읽힌다. 실측 19명 중 2명(챗지피지기) — 가입 독려 대상이 그대로 보인다
- 팀 헤더는 `참석/전체` — 6명 중 4명인지 한눈에 보인다
- 정렬은 참석 → 미정 → 미응답 → 불참. 나오는 사람이 위에 있어야 인원이 눈으로 세어진다
- **내 이름만 누를 수 있다** (참석→미정→불참 순환). 남의 응답을 대신 바꾸는 기능은
  넣지 않았다 — "계정 미보유자는 가입 독려로 해결"이라는 앞선 결정과 어긋난다
- 명단은 **회원 전용**이다 — 비로그인에게는 숫자까지만 준다(`teams: null`)
- 팀 순서는 이름순 고정 — 새로고침마다 바뀌면 어느 팀이 어디 있었는지 매번 다시 찾는다

### 1-4d. 링크 공유 ✅ 완료 — 홈 헤더로 이전

사용자 요구(2026-08-14): *"공유링크로 단톡방에 올려서 유도"* →
이어서 *"공유 링크 복사는 홈 화면 자체에 부여, 우측 상단 쯤"*.

처음엔 참여신청 카드 안에 뒀다가 **홈 헤더(팀 이름 옆) 우측 상단**으로 옮겼다
(`ShareLeagueButton`). 단톡방에 던지는 링크는 "우리 팀 페이지"이지 한 기능이 아니다.
기능 카드 안에 있으면 그 기능이 바뀔 때마다 공유 버튼 자리가 흔들리고, 찾는 사람은
매번 다른 곳을 뒤진다. **참여신청이 보류된 지금 그 판단이 맞았음이 드러났다** —
공유는 그대로 살아 있다.

- **Web Share API** 를 먼저 쓴다. 설치한 앱(PWA standalone)에서도 카카오톡이 시스템 공유
  시트에 그대로 뜬다. 카카오 SDK 는 앱키·도메인 등록·스크립트 로드가 붙는데 얻는 건
  카톡 전용 카드뿐이라 지지 않았다
- 공유 시트를 **닫은 것은 실패가 아니다** — `AbortError` 에 토스트를 띄우면 잘못한 것처럼 보인다
- 공유 시트가 없는 환경(데스크톱)은 **클립보드 복사**로 떨어지고, 아이콘이 잠깐 체크로 바뀐다
- URL 에서 **쿼리·해시를 뗀다** — 내 화면 상태(필터·탭)가 남의 링크에 묻어가면 안 된다

### 1-5. 구현하며 정한 것

- **정원 초과** — 선착순으로 자른다(409). 단 **이미 참석인 사람이 다시 눌러도 막지 않는다** —
  그 사람 자리는 이미 세어져 있다. 대기 명단은 넣지 않았다(운영진 배정 회의가 그 역할을 한다)
- **정원은 '참석'에만 건다** — 불참·미정은 자리를 차지하지 않는다
- **변경 허용 범위** — 그 날짜가 지나기 전까지 언제든 바꿀 수 있다. 당일 취소가 잦은 게
  동호회 현실이라 막으면 데이터가 실제와 어긋난다. **지난 날짜는 거부**한다 —
  사후에 명단을 고치면 그날 실제로 누가 왔는지가 흐려진다
- **알림** — 푸시가 없다. 앱 내 카드로 시작하고, 필요하면 푸시 재도입을 별건으로 판단

### 1-6. 가입 독려 (선행 과제)

사용자가 대리 신청 대신 이 길을 택했다. **참여신청의 성패가 여기 달려 있다.**

- `SignupRateCard` 가 이미 있다 — 가입률 표시 자산을 재사용한다
- 총무 화면에 **미가입 회원 목록 + 가입 링크 공유** 버튼
- ⚠ **체크포인트**: 가입률이 오르지 않으면 총무가 단톡방을 병행하게 되고, 그러면 앱 명단이
  틀린 채 남는다. 출시 전 가입률을 확인하고, 낮으면 대리 신청을 다시 논의한다

## 2. 회비 (Phase 2)

### 2-1. 실제 통장 연결 — 하지 않는다

기술 문제가 아니라 **법·책임 문제**다.

| 방식 | 판정 |
|---|---|
| 오픈뱅킹 API | 핀테크 이용기관 등록 필요 — 심사·보증보험·자본요건. 소규모 불가 |
| PG 가상계좌 | **사업자등록증 필수**. 동호회는 대개 미등록 |
| 온볼이 대신 수취 | **전자금융거래법** 자금 수취·보관 이슈. 정산·환불·분쟁 책임이 온볼로 |
| 계좌 스크래핑 | 인증정보 위임 · 약관 위반 · 보안 위험 |

**돈이 플랫폼을 거치는 순간 온볼이 금융 사업자가 된다.** 스탯 앱이 감당할 무게가 아니다.
→ 입금은 **총무 계좌로 직접**, 앱은 **장부**만 맡는다. 지금 하는 포인트 방식의 정식화다.

### 2-2. 요금 구조를 데이터로 둔다

사용자 원문: *"매월 정규회원 신청을 해서 정규회원은 1회당 비용이 조금 더 저렴, 비정규회원은
1회권인 대신 더 비쌈. **다만 대부분의 농구동호회는 월 회비 형태이고 구조는 조금씩 다를 수 있음**"*

⚠ **미라클 방식을 코드에 박으면 다른 동호회를 못 받는다.** 온보딩을 앞두고 있으므로
요금 구조는 반드시 **설정값**이어야 한다.

```sql
CREATE TABLE league_fee_plans (
  id uuid PRIMARY KEY,
  league_id uuid NOT NULL,
  name text NOT NULL,              -- '정규회원' / '1회권' / '월 회비'
  kind text NOT NULL CHECK (kind IN ('monthly','per_session')),
  amount int NOT NULL,             -- 원. 소수 없음
  effective_from date NOT NULL,    -- 금액이 바뀌어도 과거 장부가 흔들리지 않게
  effective_to date
);

CREATE TABLE league_memberships (  -- 월별 정규회원 신청
  league_id uuid, account_id uuid,
  month text NOT NULL,             -- 'YYYY-MM'
  plan_id uuid NOT NULL,
  UNIQUE (account_id, month)
);
```

**`effective_from` 을 두는 이유** — 단가가 오르면 과거 회차 금액까지 바뀐다. 배지 임계값 때와 같은
함정이다. 시점을 남겨야 지난 장부가 고정된다.

### 2-3. 원장

```sql
CREATE TABLE league_ledger (
  id uuid PRIMARY KEY,
  league_id uuid NOT NULL,
  kind text NOT NULL CHECK (kind IN ('deposit','charge','expense')),
  account_id uuid,                 -- 입금·차감이면 대상자. 지출이면 null
  amount int NOT NULL,             -- 양수. 방향은 kind 가 정한다
  occurred_on date NOT NULL,
  memo text,
  schedule_date_id uuid,           -- 회차 차감이면 어느 날 경기인지
  created_by uuid NOT NULL,        -- 기록한 어드민. 누가 넣었는지 반드시 남긴다
  created_at timestamptz NOT NULL DEFAULT now()
);
```

**입출금을 한 테이블에 두는 이유** — 투명성의 핵심은 잔액이다. 나뉘어 있으면 "지금 얼마 남았나"를
두 곳을 더해 구해야 하고, 그러면 화면마다 값이 갈린다.

**`balance` 컬럼을 두지 않는다.** 개인 잔액 = 입금 합계 − 차감 합계로 매번 계산한다.
저장하면 언젠가 원장과 어긋나고, 그때 어느 쪽이 맞는지 알 수 없다.

### 2-4. 자동화는 여기까지

총무가 은행 앱 **입금 내역을 붙여넣으면 파싱해 입금자명으로 자동 매칭**한다.
확인·확정은 사람이 한다. 이체 자체는 앱이 하지 않는다.

### 2-5. 두 기능의 연결

참석 확정(`going`) → 회차 차감(`charge`). 단가는 그 사람의 그달 `membership` 이 정한다.
**자동 차감은 기본 끄기**로 둔다 — 취소·노쇼 처리 규칙이 동호회마다 다르고, 돈이 자동으로
빠지면 항의가 온다. 총무가 확정 버튼을 누르는 흐름이 안전하다.
