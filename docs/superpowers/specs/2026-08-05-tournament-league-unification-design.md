# 대회형 → 리그형 근본 통일 설계

작성 2026-08-05. 근거는 두 건의 전수조사(코드 지도 · 데이터 매핑)이며, 수치는 전부 운영 DB 실측값이다.

## 무엇을 왜 하는가

온볼에는 같은 일을 하는 앱이 두 벌 있다.

| | 대회형 (레거시) | 리그형 (현행) |
|---|---|---|
| 주소 | `/[org]/[team]/*` | `/league/[orgSlug]/[leagueId]/*` |
| 테이블 | `teams · tournaments · games · game_events` | `leagues · league_teams · league_games · league_game_events` |
| 쓰는 곳 | 파란날개 (청년부·장년부) | 미라클모닝 |
| 컴포넌트 | 26개 · 6,300줄 | 82개 · 12,900줄 |

`leagues.mode`(`'league' | 'tournament'`, 마이그레이션 075)가 이미 있는데 **코드에서 한 번도 읽지 않는다.** 분기점으로 만들어 두고 실제로는 트리를 통째로 복제하는 쪽으로 흘렀다.

비용은 앞으로 커진다. 동호회를 새로 받을 때마다 두 벌 중 어느 쪽에 태울지 정해야 하고, 기능 하나를 고치면 두 곳을 고쳐야 한다. 이미 단계 4(상대팀 선수 기록)는 **리그 트리 안에만** 만들었다 — 방향은 그때 이미 정해진 셈이다.

**목표: 파란날개를 리그 구조로 옮기고, `mode` 를 실제 분기점으로 만들고, 레거시 트리를 지운다.**

## 확정된 사실 (실측)

### 점수는 바뀌지 않는다

가장 큰 위험이었다. 레거시는 점수를 코드에 박아 두고(`src/app/api/events/route.ts:34-45`), 리그형은 규칙 엔진으로 계산한다(`src/lib/stats/scoring.ts`). 저장값을 대조한 결과 **불일치 0건**:

| 이벤트 | 성공 건수 | 저장 총점 | 건당 |
|---|---|---|---|
| `shot_3p` | 186 | 558 | 3.0 |
| `shot_2p_mid` | 120 | 240 | 2.0 |
| `shot_layup` | 202 | 404 | 2.0 |
| `shot_post` | 157 | 314 | 2.0 |
| `free_throw` | 300 | 300 | 1.0 |

레거시 하드코딩 값이 `STANDARD_SCORING` 과 정확히 같다. 과거 기록의 총점은 이관 후에도 동일하다.

단, **레거시에는 `and_one` · `ft_2pt` · `ft_3pt_1` · `ft_3pt_2` 이벤트 타입 자체가 없다**(enum 미포함). 앤드원은 "성공 슛 + 별개의 자유투" 두 행으로 남아 있고 둘을 잇는 정보가 없다. 총점은 맞지만 **파울 종류별 세분화는 소급 복원이 불가능**하다. 이건 받아들이고 넘어간다.

### 이관 대상 규모

| 조직 | 팀 | 대회 | 경기 | 이벤트 | 선수 | 기간 |
|---|---|---|---|---|---|---|
| paranalgae | 청년부 | 8 | 36 | 4,039 | 36 | 2026-01-18 ~ 07-26 |
| paranalgae | 장년부 | 4 | 14 | 1,954 | 32 | 2026-04-18 ~ 07-05 |

부수 데이터: `tournament_players` 112행, `player_minutes` 1,525행. 고아 경기 0건(모든 `games.tournament_id` 채워짐). 완료 44 / 미완료 6.

`teams` 에 `miracle` 행이 하나 있으나 하위 데이터 0건 — 074 마이그레이션이 FK 를 채우려고 만든 껍데기다. 이관 대상 아니다.

### ⚠ 함정: `games.team_type` 을 믿으면 안 된다

**50경기 전부 `'youth'`** 로 적혀 있다. 실제로는 장년부 경기가 14건이다:

```
tournaments→teams 로 역산: senior 14 / youth 36
games.team_type 그대로:    youth 50
```

이 필드를 신뢰하면 **장년부 전체 기록이 청년부로 들어간다.** 팀은 반드시 `games.tournament_id → tournaments.team_id` 로 유도한다. (`players.team_type` 은 반대로 정확하다 — 32 senior / 36 youth 모두 일치.)

### 목적지가 절반 준비돼 있다

`leagues` 에 `org_slug='pana-basket-senior'`(id `76f91f2f-…`, 2026-05-19 생성, `status='upcoming'`) 행이 있고 하위 데이터는 0건이다. 075 마이그레이션 주석이 "현재 데이터 0건인 스텁"이라고 기록해 둔 그 행이다.

## 결정

### 1. 사라질 데이터는 버리지 않고 컬럼을 만든다

실제로 값이 들어 있는 필드를 확인했다:

| 레거시 필드 | 실데이터 | 결정 |
|---|---|---|
| `games.venue` | 50중 **33건** | `league_games.venue` 추가 |
| `games.round` (조별예선·8강·결승…) | **43건** | `league_games.round_label` 추가 |
| `games.ai_mvp` (jsonb) | **44건** | `league_games.ai_mvp` 추가 |
| `tournaments.type` (pro/amateur) | 12건 (7/5) | `league_quarters.tournament_type` 추가 |
| `tournaments.description` | **12건 전부** | `league_quarters.description` 추가 |
| `players.height_cm` | **68명 전원** (164~195) | `league_players.height_cm` 추가 |
| `players.is_pro` (선출) | 7명, 화면 노출 중 | `league_players.is_pro` 추가 |
| `players.is_active` | 비활성 3명 | `league_players.is_active` 추가 |
| `players.weight_kg` | **0건** | 버린다 |
| `games.notes` | **0건** | 버린다 |
| `game_events.notes` | **0건** | 버린다 |

`round_label` 로 이름을 바꾸는 이유: `league_games` 에는 이미 `round_num`(일정 슬롯 번호)이 있다. `round` 를 그대로 쓰면 두 개념이 같은 이름을 두고 싸운다.

### 2. 대회는 `league_quarters(kind='tournament')` 로 담는다

새 테이블을 만들지 않는다. 076 마이그레이션이 이미 `league_quarters.kind` 를 일반화하면서 `'tournament'` 를 값으로 넣어 뒀다 — 설계는 그때 끝나 있었다.

매핑: 파란날개 청년부 2026 시즌 하나 = `leagues` 1행, 그 안에 대회 8개 = `league_quarters` 8행. 장년부도 같은 방식으로 4행.

### 3. 상대팀은 이름으로 외부 팀 행을 만든다

레거시는 상대를 문자열(`games.opponent`)로만 갖는다. 구조화된 상대 선수 테이블이 있었으나 **073 마이그레이션(2026-08-04)에서 이미 삭제됐다** — 4개월간 미사용. 그 마이그레이션 주석이 후속 대체재로 `league_teams.is_external` 을 지목했고, 단계 4에서 그대로 구현됐다.

따라서 이관할 상대 선수 데이터는 **존재하지 않는다.** 팀명별로 `league_teams(is_external=true)` 행을 만들어 `away_team_id` 로 잇는다.

### 4. 되돌릴 수 있게 쪼갠다

레거시 원본은 **마지막 단계까지 건드리지 않는다.** 복사 → 대조 → 화면 전환 → 정리 순으로 가고, 각 단계는 앞 단계를 되돌리지 않고도 멈출 수 있다.

`legacy_id` 컬럼을 이관 대상 테이블에 붙인다(`league_games` · `league_players` · `league_game_events` · `league_quarters` · `league_teams`). 두 가지를 얻는다:
- **멱등성** — 스크립트를 두 번 돌려도 중복이 생기지 않는다(존재하면 갱신).
- **대조 가능성** — 원본과 사본을 행 단위로 맞춰볼 수 있다. 총합만 맞고 개별 행이 어긋나는 사고를 잡는다.

정리 단계에서 컬럼을 지운다.

### 5. `mode` 를 실제 분기점으로 쓴다

`leagues.mode='tournament'` 일 때 리그 트리가 대회용으로 동작한다. 화면을 새로 만들지 않고 **같은 화면이 분기**한다.

| | `mode='league'` | `mode='tournament'` |
|---|---|---|
| 세그먼트 호칭 | 분기 | 대회 |
| 순위표 | 리그 순위 | 대회별 성적(우승·N강) |
| 드래프트 탭 | 있음 | 없음 |
| 상대팀 | 내부 팀 | 외부 팀(`is_external`) |

### 6. 탭 이름을 통일한다

같은 개념이 두 이름을 갖고 있다. 페이지 안 제목은 이미 양쪽 다 "하이라이트"라 **탭 라벨만** 어긋난 상태다.

| 레거시 라벨 | 리그 라벨 | 통일 |
|---|---|---|
| 영상 | 하이라이트 | **하이라이트** |
| 통계 | 스탯 | **스탯** |
| 선수 | 라커룸 | **라커룸** |
| 대회 | — | **대회** (`mode='tournament'` 전용) |

레거시 트리를 지우면 라벨 문제는 자연히 사라진다. 별도 작업이 아니다.

## 단계 구성

각 단계는 그 자체로 배포 가능하고, 다음 단계 없이도 시스템이 정상 동작해야 한다.

### A. 목적지 준비 (스키마)
리그 테이블에 보존 컬럼과 `legacy_id` 를 추가한다. 화면 변화 없음. 기존 두 동호회에 영향 없음.

### B. 데이터 복사
파란날개 레거시 데이터를 리그 테이블로 복사한다. **원본 무손상.** 대조 스크립트가 경기 수·이벤트 수·선수별 총득점·팀 귀속을 원본과 맞춰 증명한다. 화면은 아직 레거시를 본다.

### C. 화면 전환
`mode='tournament'` 분기를 리그 트리에 넣고, 파란날개 주소를 리그 주소로 넘긴다. 이 시점에 사용자가 새 화면을 본다. 문제가 생기면 리다이렉트만 되돌리면 레거시로 복귀한다.

### D. 레거시 정리
`(main)` 트리 · 레거시 API 23개 · 레거시 테이블 · `legacy_id` 컬럼을 지운다. C 가 충분히 검증된 뒤에만 한다.

곁다리로 **완전히 죽은 코드**가 있다: `src/app/(main)/[org]/league/*` 219줄. 초기 리그 구현의 잔해로 어디서도 링크되지 않고 미들웨어도 태우지 않는다. D 에서 함께 지운다.

## 위험과 대비

| 위험 | 대비 |
|---|---|
| 장년부 기록이 청년부로 섞임 | `tournament_id → team_id` 로만 유도. 대조 스크립트가 팀별 경기 수(36/14)를 검증 |
| 사본과 원본의 득점이 어긋남 | 선수별 총득점을 원본 대비 전수 대조. 하나라도 다르면 중단 |
| 이관 도중 중단 | `legacy_id` 로 멱등 — 재실행 안전 |
| 미라클이 영향받음 | 모든 단계에서 `verify-schema.mjs` · `verify-scoring.mjs` 통과 필수 (미라클 7114점 · 45명 · 271경기 불변) |
| 파란날개 회원이 옛 주소로 들어옴 | 리다이렉트 유지. `/youth` · `/senior` 짧은 주소도 새 주소로 재연결 |
| 레거시 삭제로 어드민 깨짐 | 어드민 대시보드 집계·org 상세가 레거시 테이블을 직접 읽는다 — D 에서 함께 전환 |

크론 2종(배지 재계산 · 유튜브 동기화)은 리그 테이블만 읽는다. 레거시 삭제로 깨지지 않는다.

## 손대지 않는 것

- **미라클 리그 데이터** — 이번 작업의 어느 단계에서도 건드리지 않는다.
- **`src/lib/stats/perDayStats.ts`** — 조사 보고서 하나가 "소비자 0건, 죽은 모듈"이라 적었으나 **사실이 아니다.** 스트릭·마일스톤이 쓰는 살아 있는 인프라이며 단계 4에서 방금 수정했다. 삭제 후보로 올리지 않는다.
- **`teams` 테이블** — 레거시 전용이 아니다. 074/075 이후 `leagues.team_id` 가 참조하고 082 의 공개/비공개 상태도 여기 있다. 양쪽이 공유하는 조직 레지스트리이므로 D 에서도 남긴다.
