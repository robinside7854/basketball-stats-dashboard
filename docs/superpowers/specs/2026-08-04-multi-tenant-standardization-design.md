# 멀티테넌트 표준화 설계

작성일: 2026-08-04
상태: 설계 승인 완료 · 구현 계획 대기

## 배경

다른 동호회로 확장하기 위한 표준화. 지금까지는 범용성보다 맞춤 커스터마이징을 우선해 왔고,
그 결과 특정 팀(파란날개·미라클모닝)에 종속된 구조가 남아 있다.

### 현재 상태 실측 (2026-08-04)

이벤트 기록 스택이 **세 벌**로 중복되어 있었다.

| 스택 | 용도 | 테이블 | 처리 |
|---|---|---|---|
| 1 | 우리팀 대회 기록 | `games` · `game_events` | 통합 대상 |
| 2 | 내부 리그 기록 | `league_games` · `league_game_events` | **정본** |
| 3 | 상대팀 정찰 기록 | `opponent_*` 5종 | **제거 완료** (073) |

세 스택 모두 `quarter / type / player / result / related_player / points` 로 스키마가 동일했다.
같은 것을 세 번 만든 상태였고, 이것이 표준화가 필요했던 실질적 이유다.

정찰 스택은 4개월 미사용(마지막 기록 2026-04-04)이라 코드 2,523줄 + 테이블 5개를 제거했다.
정찰 선수는 회원이 아니어서 통계 자격·배지·랭킹·인증 게이팅에서 전부 예외 처리가 필요했고,
이 예외 덩어리가 통합 설계를 가장 복잡하게 만들던 요인이었다.

### 리그 트리는 이미 표준화에 근접해 있다

`src/app/league` + `src/components/league` 30,532줄 중 테넌트 하드코딩은 13곳이고,
그중 **로직 분기는 0건**이다. 나머지는 주석·placeholder·fallback 문자열이다.
팀명·리그명·팀 컬러·라운드 수·분기 구성은 전부 DB에서 오고, URL도 `orgSlug`/`leagueId` 로 파라미터화되어 있다.

또한 `badges.ts` 는 **이미 두 트리가 공유**하고 있다(리그 2곳 + 레거시 3곳).
"정규화된 입력을 받는 순수 함수" 패턴이 이 저장소에서 이미 검증됐다는 뜻이다.

## 확정된 결정

| 항목 | 결정 | 근거 |
|---|---|---|
| 모드 단위 | **시즌 단위 속성** | 한 동호회가 내부 리그와 외부 대회를 동시 운영할 수 있어야 함 |
| 레거시 대회 기록 | **전면 통합** — 이관 후 `/(main)` 트리 제거 | 코드 한 벌 유지 · 파란날개도 신규 통계 기능 수혜 |
| 룰 설정 범위 | **핵심 룰만 설정화** | 통계·배지·어워즈는 전 팀 동일해야 표준화가 성립 |
| 스키마 정본 | **`league_*` 흡수** (테이블명 유지) | 82개 API·최신 기능이 이미 이 위에 있음 |
| 대회형 팀 구성 | **우리 팀 1개 + 외부 상대팀 N개** | 대회에서는 단일 팀만 관리 |

### 테이블명을 바꾸지 않는 이유

`league_*` 가 대회까지 담게 되면 이름이 실제와 어긋난다. 그럼에도 유지하는 이유는
Supabase 쿼리가 `.from('league_players')` 처럼 **문자열이라 타입 체커가 누락을 잡지 못하기** 때문이다.
30,000줄 전역 치환에서 한 곳만 놓쳐도 런타임에서 터진다. 사용자에게 노출되지 않는 내부 명칭이므로
가독성 이득보다 리스크가 크다. 필요해지면 이후에 뷰로 별칭을 준다.

### 채택하지 않은 접근법

- **제3의 통합 스키마 신설** — 이름과 구조는 정확해지나 82개 API 전부 재작성. 사실상 재개발.
- **스키마 유지 + 읽기 어댑터만 통합** — 마이그레이션은 0이지만 쓰기 경로가 둘로 남아
  새 기능마다 두 번 만들어야 한다. "전면 통합" 결정과 어긋난다.

## 아키텍처

### 1. 조직 · 시즌 계층

```
orgs (신설)
  id · slug · name · brand_color · logo_url · status
   └── seasons  (기존 leagues 를 개념 확장)
         id · org_id(FK) · slug · name · year
         mode: 'league' | 'tournament'
         rules JSONB
          └── league_teams · league_players · league_games · league_game_events
```

핵심은 **`seasons` 아래는 두 모드가 완전히 같은 테이블을 쓴다**는 점이다.
통계 코어가 하나로 유지되는 이유가 이것이다.

현재 `org_slug` 는 `teams` 와 `leagues` 에 TEXT 로 중복 저장되어 있고 FK 가 아니다.
즉 조직은 테이블이 아니라 문자열 관습이며, 로고·브랜드 컬러·소유자·상태를 담을 곳이 없다.
어드민의 "조직 생성"도 실제로는 `teams` 행 삽입이다. `orgs` 테이블 신설로 이를 정규화한다.

### 2. 두 모드의 차이 — `league_teams.is_external` 한 컬럼

| | 리그형 | 대회형 |
|---|---|---|
| 팀 구성 | 내부 팀 N개 (`is_external=false`) | 우리 팀 1개 + 외부 상대팀 N개(`is_external=true`) |
| 순위표 | 전체 팀 라운드로빈 | 우리 팀 전적만 |
| 선수 통계 | 전원 집계 | `is_external=false` 팀 선수만 집계 |
| 라운드 | 경기일 = 1라운드 (설정 가능) | 대회 = 그룹 단위 |

외부 팀 선수는 `league_players` 에 등록하지 않는다. 대회형에서 상대팀은 **점수 집계 단위로만** 쓰이며,
상대 선수별 기록은 정찰 기능 제거와 함께 범위에서 빠졌다.
향후 필요해지면 `is_external=true` 팀에 선수를 붙이는 형태로 확장한다 — 통계 자격 판정은
이미 `is_external` 로 갈리므로 추가 예외 로직이 필요 없다.

### 3. 룰 설정 (`seasons.rules` JSONB)

"운영 방식만 팀별로"를 담는 그릇. 현재 집계 로직에 하드코딩된 미라클모닝 전용 룰이 여기로 나온다.

```jsonc
{
  "scoring": {
    "three_point": 3,
    "free_throw": { "single": 1, "and_one": 1 },
    "plus_one_bonus": 0        // 미라클모닝만 1 (3점→4점)
  },
  "period": { "count": 4, "minutes": 7 },
  "round_unit": "day",         // "day"(미라클모닝) | "game"
  "qualification": { "min_round_ratio": 0.3 },
  "tracking": { "fouls": true, "minutes": true }
}
```

집계 로직은 **한 벌**이고 이 설정을 파라미터로 받는다.
현재 `detail/route.ts` 의 `isPlusOne ? 4 : 3`, `ft_2pt` 2점 처리, 하루=1라운드 그룹핑이 대상이다.

기본값은 **일반적인 아마추어 농구 룰**(3점=3, 자유투 1점, plus_one 없음, 파울 기록)로 둔다.
미라클모닝만 예외 설정을 갖는다. 그래야 새 동호회 온보딩 시 아무것도 건드리지 않아도 정상 동작한다.

통계·배지·어워즈·마일스톤 카테고리는 **설정 대상이 아니다**. 전 팀 동일하게 유지한다.
팀마다 화면이 달라지면 표준화가 희석되고 지원이 어려워진다.

### 4. 브랜딩

컴포넌트가 이미 전부 `--mm-*` 토큰을 참조하므로(디자인 통일 작업의 산물),
레이아웃 한 곳에서 `orgs.brand_color` 로 토큰을 덮어쓰면 된다. 30,000줄 중 손댈 파일은 `layout.tsx` 하나다.

`manifest.ts` 도 org별 동적 생성으로 바꾼다. 현재 `start_url` 이 `/league/miracle/2026` 으로 고정되어 있어
설치형 PWA 가 미라클모닝 전용이다.

`appleWebApp.title`('미라클모닝')과 manifest `name`('미라클모닝 농구단')도 org 값으로 치환한다.
단 **이미 홈 화면에 추가한 사용자의 아이콘 이름이 바뀌므로** 배포 시 공지가 필요하다.

## 마이그레이션 전략

레거시 대회 기록을 통합 스키마로 옮기는 경로는 이미 검증되어 있다 —
2025 시즌 임포터(`scripts/import-2025.mjs`)가 **과거 박스스코어를 이벤트로 합성해 넣고,
`leagueStats` 와 같은 규칙으로 재집계해 원본과 대조**하는 방식을 쓴다. 이 패턴을 재사용한다.

### 매핑

| 레거시 | 통합 후 | 비고 |
|---|---|---|
| `teams.org_slug` | `orgs` 1행 | `paranalgae` → 조직 1개 |
| `teams.sub_slug` | `seasons` 분리 | `youth`/`senior` 는 **조직이 아니라 시즌으로 분리**. 두 팀이 각각 대회를 뛰므로 연도×서브팀 조합마다 시즌 1개 |
| `tournaments` | `seasons` 1개 = 대회 1개 | 대회 자체가 시즌 단위. 시즌 내 그룹 개념은 도입하지 않음 |
| `players` | `league_players` | 우리 팀 선수만. 소속 시즌마다 행이 생김 |
| `games` | `league_games` | 상대팀은 `is_external=true` 팀으로 생성 |
| `game_events` | `league_game_events` | |
| `player_minutes` | `league_player_minutes` | |

`sub_slug`(youth/senior)를 조직이 아닌 시즌으로 내리는 이유는, 두 팀이 같은 조직의 하위 조직이고
브랜드·회원 계정·관리자를 공유하기 때문이다. 조직을 둘로 쪼개면 이 공유가 깨진다.

### 검증 게이트

이관 후 **원본과 집계 결과가 일치하지 않으면 커밋하지 않는다.**
2025 임포터와 동일하게 dry-run 기본, `--commit` 명시 실행으로 만든다.
특히 `plus_one` NULL 폴백으로 과거 득점이 틀어지는 케이스는 오류로 차단한다.

## 단계별 실행

| 단계 | 내용 | 산출물 |
|---|---|---|
| **0** | 정찰 기능 제거 | ✅ 완료 (`747f8de4`, `0f8c47f9`) |
| **1** | `orgs` 테이블 + `seasons.mode`/`rules` + `league_teams.is_external` | 마이그레이션 · 백필 |
| **2** | 룰 엔진 — 하드코딩된 미라클모닝 룰을 `rules` 참조로 전환 | 집계 로직 한 벌 |
| **3** | 브랜딩 런타임 주입 + `manifest` 동적화 | `layout.tsx` · `manifest.ts` |
| **4** | 레거시 대회 기록 이관 (dry-run → 검증 → commit) | 이관 스크립트 |
| **5** | `/(main)` 트리 + 레거시 API 44개 제거 | 코드 한 벌 |
| **6** | 온보딩 마법사 (조직 → 시즌 → 팀 → 선수 CSV) | 어드민 UI |

단계 1~3은 기존 동작을 깨지 않는 순수 추가이므로 먼저 배포 가능하다.
단계 4~5가 되돌리기 어려운 구간이므로 그 앞에서 한 번 끊는다.

## 검증 방법

- **단계 1~3**: 미라클모닝 리그 화면이 이전과 **픽셀 단위로 동일**해야 한다.
  룰을 설정으로 뺐어도 미라클모닝 설정값이 기존 하드코딩과 같으면 결과가 같아야 한다.
- **단계 4**: 이관 전후 선수별 시즌 합계(PTS/REB/AST/STL/BLK/FGM/FGA)가 정확히 일치.
- **단계 6**: 신규 동호회 하나를 코드 수정 없이 온보딩 완료.

## 열린 항목

- 온보딩은 운영자(개발자)가 수행한다. 셀프서비스 가입은 범위 밖.
- 조직 단위 권한 경계(org 관리자 role)는 현재 리그별 `edit_pin` + 회원 role 위에 얹어야 한다.
  `8a987033` 에서 PIN → 로그인 회원 role 전환이 시작됐다. **단계 1에는 포함하지 않고**,
  그 전환이 끝난 뒤 별도 스펙으로 다룬다 — 지금 함께 손대면 인증 변경과 스키마 변경이
  같은 배포에 섞여 문제 원인 추적이 어려워진다.
- 선수 식별: 한 사람이 두 동호회에 속하는 경우 org별 별도 행으로 둔다(교차 조직 신원 통합은 YAGNI).
